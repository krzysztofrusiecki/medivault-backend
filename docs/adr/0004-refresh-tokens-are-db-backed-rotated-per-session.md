# Refresh tokens are DB-backed, rotated per use, and scoped to independent per-login Sessions

Status: accepted

Sign-in now issues two credentials: a short-lived (15 min) access token, unchanged in shape (signed JWT, `{ sub, email, role }`, `Authorization: Bearer`), plus a `RefreshToken` — a DB-backed, hashed, opaque random string delivered as an httpOnly cookie (`Path=/api/auth`, `SameSite=Lax`, `Secure` in production) with a 30-day expiry. Every call to `POST /auth/refresh` rotates it: the presented row is marked used, a new row is issued in its place, and the access token's TTL resets. A user may hold several concurrent `Session`s at once (e.g. phone and laptop) — each login starts its own independent rotation lineage, identified by a stable `familyId` that survives rotation. `POST /auth/logout` reads that `familyId` off the presented refresh cookie itself (hash it, look up the row, take its `familyId`, cross-check the row's `userId` against the access token's `sub`) and revokes every row sharing it — so the access token never needs to carry session identity itself, and the cookie's `Path` covers `/api/auth` broadly rather than being scoped to `/auth/refresh` alone, so it reaches both `/auth/refresh` and `/auth/logout`. If a refresh token is presented after it's already been rotated away (a replay/theft signal), the entire `Session` — every row sharing that `familyId` — is revoked, not just the reused row.

`JWT_EXPIRATION` (validated but unused since the original JWT-only auth) is removed; `ACCESS_TOKEN_EXPIRATION` and `REFRESH_TOKEN_EXPIRATION` replace it as two explicit, separately-tunable lifetimes.

We considered a stateless refresh token (a second signed JWT, no server-side record) to avoid a new table, but rejected it: neither logout nor rotation-with-reuse-detection is meaningfully implementable without something to revoke against, and a JWT blocklist is a database table by another name — so we built the table directly. We considered a single active session per user (new login invalidates the previous one), which is simpler, but rejected it as the wrong trade for a token-rotation design: if single-session were the goal, plain server-side session auth would have been the simpler choice outright; multi-session is also what makes per-login `familyId` (and therefore scoped logout and scoped reuse-detection) meaningful rather than redundant with the user id. We considered having logout revoke every session for the user, but rejected it as not matching what "log out" conventionally means on one device. We also considered carrying `familyId` as a `sid` claim on the access token instead (so logout wouldn't need the cookie at all), but rejected it: session identity only exists to support logout, and putting it on the access token means every access token — used on every request — carries session state that's irrelevant everywhere except one rarely-hit route. Reading it from the refresh cookie keeps the access token unchanged and confines the widened cookie `Path` to auth routes only.

Deferred on purpose: expired/revoked `RefreshToken` rows are filtered out at query time (`expiresAt > now AND revokedAt IS NULL`), not deleted — periodic pruning is tracked separately as [MV-38](https://linear.app/krzysztofrusiecki/issue/MV-38/prune-expiredrevoked-refreshtoken-rows-cron) and isn't blocking. Revisit this ADR if a "manage active sessions" or "log out everywhere" feature is wanted later — both would need a listing endpoint over a user's `Session`s that doesn't exist yet.
